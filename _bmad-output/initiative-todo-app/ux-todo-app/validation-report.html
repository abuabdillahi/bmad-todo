BMad Todos (Todo App v1) — UX Design Validation Report

_bmad-output/initiative-todo-app/ux-todo-app/EXPERIENCE.md · DESIGN.md unchanged in this update · Update: amended architecture spine

Every item in review-reconcile-ux-update.md now reads correctly in EXPERIENCE.md. No sentence contradicts a binding AD, and the announce callers and kinds, list-state conditions, Try again timing, failure kinds, per-call promise, and the "Landed after all" row all match the spine. Three medium gaps remain. Each is a place where EXPERIENCE relies on something the spine or EXPERIENCE itself leaves unstated: the failure kind behind the List error panel's text, a failed add that removes a card the user is editing or focused in, and the after-delete focus rule applied to removals no user started. One of them needs a small spine addition (candidate Flag 11).

On accessibility, the update holds up. The reviewer found no AA failure in the spec as written, and every fix from the earlier review still stands: live regions are mounted empty, repeats are cleared and set again, focus is handed off first, and no timers are used. The remaining risk sits in what happens without a user action: focus moved by a refetch, list changes nobody announces, and the replace-as-you-type rule. Any of these could ship as a lost-focus bug or a misleading screen-reader experience if built literally. All of them can be fixed inside AD-11, AD-13 and AD-14, or documented as accepted.

Spine consistency review

review-spine-consistency.md

Every item in review-reconcile-ux-update.md now reads correctly in EXPERIENCE.md (29 resolved, 1 n/a: the capability-map R5 wording, which is spine-side and cosmetic). No sentence contradicts a binding AD. Three medium gaps remain, each a place where EXPERIENCE relies on something the spine or EXPERIENCE itself leaves unstated. One of them needs a small spine addition.

medium

The List error panel's reason needs a failure kind that the store does not hold

State Patterns › List states, Error and Add during Error, L209, L215; Voice and Tone, L104; Component Patterns › Loading status, L192, List error panel, L194
AD-11 lists the todos store's contents as loaded, last fetch failed, retry requested, the pending-mutation count and the revert records, with no failure kind. The panel text is lead.load + " " + reason[type]. In "Add during Error" the helper's optimistic setQueryData resets the query's error to null, so a builder who reads the reason from the query loses it. Separately, L194 ("changes only when it succeeds") leaves open whether a failed automatic refetch with a different kind (network → unavailable) updates the reason; if it does, the change is silent, because the Loading status speaks only on entering error.
Fix: In L104, state that the reason comes from the kind of the last recorded fetch failure, held in the todos store, and add candidate Flag 11. In L194, add: "A failed automatic refetch updates the reason in place without speaking."
medium

A failed add that removes a card the user is editing or focused in has no rule

State Patterns › Row states, L234–235; Add form states › Add failed, L249; Focus management, L286, L288; Hand-off order, L298
AD-14 lets the list area announce "deleted elsewhere" only when a refetch removes a todo whose row is in edit mode, and AD-11 unmounts any removal other than a user-confirmed delete at once. L235 and L298 cover removals by "not-found or a refetch"; nothing covers the helper removing a card when its add fails while the card has an open Edit form or holds focus. A list area that detects "my editing row left the cache" also fires on this revert, replacing "Couldn't add “{t}”. …" with a false "“{t}” was deleted elsewhere.", and focus inside the removed card drops to <body>. The Motion table doesn't say whether the removed card animates.
Fix: Add a Row states row: "Edit open or focus inside, its add fails | The card unmounts at once with no motion, the edit draft is discarded, and only the helper's add failure is announced; the list area does not announce deletedElsewhere. Focus: see Focus management." Widen L288 and L298 to "by not-found, a refetch, or a failed add". In L235, say a row whose revertedAt(id) was set in the same update is a helper revert, not a refetch removal (AD-13 records a revert time for every failed todo, creates included). No spine change is needed.
medium

The after-delete rule falls back to "the add field or heading" for removals that no user started

Focus management, L282, L288
AD-11 leaves focus for a refetch removal to UX. L288 applies the after-delete rule, which on a now-empty list ends at "the add field or heading", chosen by activation type (L271). An automatic removal has no activation; L291 recognises this for the panel case and picks the Page heading. The target for the commonest refetch-removal case is undefined, so the component test L298 promises can't assert one target.
Fix: In L288, write "The after-delete rule, except that an empty list sends focus to the Page heading (no activation decides, as for the List error panel)."
low

Detecting that focus was inside an element a refetch removed is not specified

Hand-off order, L298
By the time the list area's layout effect runs, the removed node is detached and document.activeElement is already <body>, so the effect alone can't tell "focus was inside the removed row or panel" from "focus was already on the body". This is buildable inside AD-11's layering, because the list area is a component.
Fix: Add: "the list area tracks the row or panel that holds focus (a focusin listener on the list area, or a check in the removed row's layout-effect cleanup, which runs before its DOM is removed)".
low

"While revertedAt(id) is recent" has no window

State Patterns › Row states › Reverted, L228
AD-13 provides only a time. The flag lasts {motion.duration-revert} (Motion, L311, L326), but L228 doesn't tie "recent" to that length, and a card restored after a failed delete mounts later than the revert time.
Fix: Write "while less than {motion.duration-revert} has passed since revertedAt(id); a card that mounts inside that window shows the flag for the time that remains".

Candidate new flag for the architect — Flag 11: Failure kind of the last fetch. UX need: the List error panel and the Loading status say "Couldn't load your todos." plus the reason for the last fetch's failure kind (network, unavailable, or generic); the panel must keep that reason while optimistic adds go into the cache (Add during Error), and update it when a later fetch fails with a different kind. AD touched: AD-11 (todos store contents), AD-9 (failure kinds). Proposal: the query function records the failure kind with last fetch failed, e.g. lastFetchFailure: FailureKind | null in place of a boolean; cleared on success, unchanged on a cancellation, never touched by cache writes. The list area reads it from the store, not from the query's error.

Stale references.

  • "As proposed" now refers to text that is gone: Flag 1 (L448), Flag 3 (c) and (d) (L465–466), Flag 7 (L486), and Flag 9 (L496, "first option of each alternative"). Drop the phrases or change each to "accepted".
  • Flag 4's resolution (L471) names only loaded and last fetch failed; add retry requested (used in L202 and AD-11).
  • Open Items is missing three body [ASSUMPTION]s (all pre-existing): the character counter "spoken only on crossing" (L161); the inline error clearing on the next valid input (L163); focus after "Row removed by not-found or refetch while focus is inside it" (L288). The Focus row in Open Items (L542) lists only the List error panel case. Add the three to the "Introduced in distillation…" table.
  • No "pending flag N" wording, no storage-unavailable, no "or aborted", and no flag-tagged Open Items rows remain. DESIGN.md has no stale flag references.

Accessibility review

review-accessibility.md

The update holds up. No AA failure in the spec as written, and every fix from the earlier review still stands. The remaining risk sits in what happens without a user action: focus moved by a refetch, list changes nobody announces, and the replace-as-you-type rule. All of it can be fixed inside AD-11, AD-13 and AD-14, or documented as accepted.

medium

Automatic recovery lands focus on an actionable checkbox, and the user still doesn't hear what loaded (WCAG 2.4.3, 3.2.2)

§ Interaction Primitives › Focus management, line 291
A screen-reader user waiting on Try again for the Wi-Fi gets focus moved to "Pay rent, checkbox, not checked" when a reconnect refetch succeeds. They hear one todo, not that the list loaded or how many items it has, and pressing Space or Enter expecting Try again (NVDA browse mode clicks on Enter) toggles a todo they never chose. On an empty list the heading target says "BMad Todos, heading level 1", not "No todos yet."
Fix: Target the list area element that just rendered: the Todo list <ul role="list" aria-label="Todos" tabindex="-1"> ("Todos, list, 3 items") or the Empty panel <p tabindex="-1"> ("No todos yet."). Neither is a tab stop or actionable, and neither opens the phone keyboard. Tab then reaches the first Completion check. Add both to the focus-ring rule.
medium

Recovery and a successful Try again are silent for anyone whose focus is outside the panel (WCAG 4.1.3, 1.3.1)

§ Component Patterns › Loading status, line 192; § State Patterns › List states "Error, recovered without Try again", line 210; Flow 3 failure path, line 422
The Loading status voiced the load error; the reconnect refetch then replaces the panel silently while focus stays in the add field, so the screen-reader user's last spoken state is still the error and they may keep adding into what they think is a broken app. A successful Try again says "Loading your todos" and then nothing. Strictly not a 4.1.3 failure, but visual and spoken states disagree, and AD-14 has no live route for a load success.
Fix: Record it as an accepted gap: add an Open Items [ASSUMPTION] "Recovery from the List error panel, by Try again or by an automatic refetch, is not spoken (AD-14 has no route); focus moves only if it was in the panel", and add it to the Accessibility Floor's manual-pass expectations. If the user won't accept the gap, raise a new flag for Winston: a one-time utterance by the Loading status at the not-loaded → loaded transition (then "New flags from this update: none" changes).
medium

"Landed after all" leaves a false failure message on screen, and screen-reader users are the ones who will resubmit (WCAG 4.1.3, 3.3.4)

§ State Patterns › Row states "Landed after all", line 238; Flow 4 step 7, line 436
If Jun's add had landed, the banner keeps "Couldn't add “Call landlord”. …", the field still holds the restored text, and the refetch silently adds the card. A screen-reader user in the add field hears nothing, trusts the failure, presses Enter and creates a duplicate. The completion case contradicts itself the same way: the banner says "so it's still open" while the checkbox is checked.
Fix: Inside AD-13, via the per-call promise: the Add form knows its failed call's id; if that id later appears in the ['todos'] cache and the field still holds exactly the restored text, clear the field back to "0/200" without moving focus. Extend the Open Items "Landed after all" row: "the failure message is not retracted, and no screen-reader cue marks the reconcile".
medium

Refetch-driven focus moves are underspecified in four ways that can lose or steal focus (WCAG 2.4.3)

§ Focus management, lines 288, 291; § Hand-off order, line 298
Detection: after the commit, panel.contains(document.activeElement) can't be tested (the panel is detached, activeElement is <body>), so a literal build never fires; testing "activeElement is body" fires falsely after a touch tap on blank page area. Inert rows: "the first/next todo" can be an inert Leaving row, so focus() fails. No activation: line 288's after-delete rule ends in "add field or heading" but no activation chooses; line 291 picks the heading, so the rows disagree. Order: unspecified whether focus moves before or after the "deleted elsewhere" announcement.
Fix: Add to Hand-off order: focus-inside is recorded before the removing commit (a focusin/focusout-tracked flag on the row and the List error panel), and the layout effect moves focus only if that flag was set and activeElement is now <body>; focus targets skip Leaving rows; with no user activation, an empty list sends focus to the Page heading; focus moves before announce is called. Extend the component test to cover both sides (focus elsewhere stays put; focus inside lands on the target).
medium

Optimistic rows must keep their identity when the list becomes loaded (WCAG 2.4.3, 3.3.7)

§ Information Architecture › List area exceptions, line 39; § List states "Add during Loading" and "Error, recovered without Try again", lines 210, 214
Before load, optimistic adds render in a Todo list above the skeletons or List error panel; once loaded, the list area renders the cache. If those are different subtrees, or rows change key or parent, a user focused in a new card's checkbox or Edit form has the row remounted under them: focus drops to <body> and the edit draft is lost. No focus row covers this, because the row is not "removed".
Fix: Add to Component Patterns › Todo list: "The same <ul> and the same row key (the todo id) are used before and after the first successful load, so focus, an open Edit form, and an open Delete confirm survive the transition." Add a component test keeping focus in an optimistic card's edit Text field across the first successful load.
medium

Replacing characters "as it enters the field, typed or pasted" can break caret position and undo, and "typed" invites a Tab trap (WCAG 2.1.2, 3.3.2)

§ Component Patterns › Text field, line 159; Character counter, line 161
Tab never types a tab into a textarea; reading "typed tabs" as an instruction to intercept Tab creates a keyboard trap. Rewriting the controlled value on input jumps the caret to the end after a mid-text paste, Chrome drops undo history on programmatic changes, and rewriting during composition breaks IME. "Exactly what will be saved" is also not quite true: the field shows leading/trailing spaces the counter excludes.
Fix: Reword: "Tab is never intercepted and always moves focus. Forbidden characters arriving by paste, drop, autofill, or dictation are replaced: in beforeinput for insertFromPaste/insertFromDrop, by cancelling and inserting the cleaned text through the editing API so undo stays one step; otherwise on input, by restoring selectionStart/selectionEnd (safe, as each replacement is one-for-one). The value is never rewritten while isComposing." Change "exactly what will be saved" to "what will be saved, apart from leading and trailing spaces, which the counter already excludes". Add a K1 case for a mid-text paste checking caret position and Ctrl+Z.
medium

"Deleted elsewhere" after a 404 can be cut off by the focus move one round trip later, and can be spoken twice (WCAG 4.1.3)

§ Row states "Not found", line 230; Focus management, line 288; Overrides, line 98; Completion check, line 173
Cut off: toggling a todo deleted elsewhere announces "“Buy milk” was deleted elsewhere."; the refetch removes the row a round trip later and the focus move makes NVDA/JAWS cut the message mid-sentence. Spoken twice: the checkbox stays operable in edit mode, so a 404 on complete there makes the helper announce, then the refetch removing a row in edit mode makes the list area announce the identical text, cleared and set again.
Fix: Let the row react to its call's promise (AD-13 permits local reactions): on failed with kind not-found, if focus is inside the row, apply the after-delete rule then, in the same task as the helper's announcement. Add to the "Edit open, todo vanishes on refetch" row: "skipped if the current undismissed message is already “{t}” was deleted elsewhere for this todo."
low

The Loading status's timers need to be reset on each state entry (WCAG 4.1.3)

§ Component Patterns › Loading status, line 192
Speaking on every entry makes overlapping timers possible: an error at t=0, Try again at 4.9 s and a fast failure let the old 5 s clear empty the new error before it is spoken. No rule clears the previous error text on entering loading, so a stale "Couldn't load…" sits under the skeletons in browse mode.
Fix: Add "Each entry into loading or error empties the status and cancels any pending 500 ms or 5 s timer before starting its own."
low

Announcer repeats and replacements (WCAG 4.1.3)

§ Component Patterns › Announcer › Replacement, line 152
Refresh repeats: offline with the list loaded, every window focus and reconnect clears and re-sets the identical refresh message, so the full sentence is heard on every return. Status over failure: AD-mandated, but "Added" right after a failure can replace it before a polite screen reader speaks it, and sighted users lose it too.
Fix: For kind refresh only, leave an identical message that is still showing as it is, with no clear-and-set. Note the status-over-failure case as accepted in the Accessibility Floor's manual-pass expectations.
