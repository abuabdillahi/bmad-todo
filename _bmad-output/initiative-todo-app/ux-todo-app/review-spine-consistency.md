# Spine consistency review: UX spines vs architecture spine

## Verdict

**Mostly consistent, but not buildable as written.** I found no new place where the UX directly contradicts a binding AD. Ids, ordering, PATCH bodies, the AD-8 rule, React-only escaping, the one-helper data path, and CSS Modules with tokens are all used correctly. However, there are three **high** findings. Each one forces a builder to reinterpret AD-9, AD-11 or AD-13:

- A refresh failure overwrites the specific failure message.
- Adding while the list is in its Error or Loading state can end in a false Empty state.
- A network error gets its own wording, although AD-9 treats it as a generic failure.

Of the five existing flags, two are accurate as stated (1, 2). One is accurate but incomplete (3). Two are inaccurate in their framing or proposal (4, 5). Flag 5's subject is the closest the UX comes to contradicting a binding AD. If Winston rejects it, it becomes a critical finding.

Counts of new findings: **critical 0 · high 3 · medium 10 · low 11**.

## Existing flags (EXPERIENCE.md, "Architecture flags for Winston")

| # | Verdict | Notes |
|---|---|---|
| 1 — server `400` after an optimistic add or edit has no open field | **Accurate** | The tension is real, and it is inside the spine itself. AD-13 requires the helper to announce *every* failure, while AD-8 and AD-14 say field errors never go through the announcer. The flag is wrong on one detail. "No open field" is true for edit. For add, though, EXPERIENCE restores the text into the add field when the field is empty, so an inline fallback *is* possible in that case. The proposed reason, "Keep it to 1–200 characters.", is also wrong for every other cause of a `400` (an unknown field, a null, a non-UUID id; see I11). The client can't produce those, but the copy should not claim a length problem. Suggest "validation" falls back to the generic reason unless `errors[].field === 'description'`. |
| 2 — `\n` in `description` | **Accurate** | AD-8 trims and counts code points, and says nothing about line breaks or other control characters. I11 doesn't cover them either. The flag misses one thing. Other API clients, the e2e `beforeEach` setup or the contract suite could still store a `\n`, so the UX also needs a rule for *rendering and editing* an existing multi-line description. Today that text collapses to a space under normal `white-space`. In the edit field, the paste rule would silently convert it. |
| 3 — failed-add restore needs a helper callback; leaving row outlives the cache | **Accurate but incomplete** | AD-13 doesn't define the helper's API. TanStack's per-call `mutate(vars, { onError, onSuccess })` already gives the add form a callback, so the tension is mild. The flag misses four things. (a) "Delete success announced on server confirmation" needs the same per-call success path. (b) The revert flag needs a per-todo "just reverted" signal from the helper to the card (see the medium finding below). (c) Leaving rows also come from refetch removals (not-found, a row vanishing while in edit), not only from delete. (d) A leaving row in the `<ul>` and the Empty panel can be on screen together, which breaks the IA rule "exactly one of". It also cites "AD-11 (list renders the cache)". AD-11 actually says hooks only, one key, server order. |
| 4 — add during the first load; the cancel could leave only the new todo | **Inaccurate (proposal and scope)** | The mechanism is right. In TanStack, `cancelQueries` reverts the pending query, and the optimistic `setQueryData` then makes it `success` with `[newTodo]`. The proposal is wrong, though. "Confirm the helper refetches after the mutation" is already AD-13's rule ("invalidates `['todos']` only when no todo mutation is still pending"). "Or doesn't cancel the initial load" would break AD-13's first bullet. The real gap is not flagged: the window before the refetch, and above all the **failure** branch, can end in a false Empty state (high finding H2). The State row "the rest of the list must not look emptied" also names no treatment, so it can't be built. |
| 5 — hidden Loading status and the field-local over-limit region are extra live regions | **Inaccurate (understates)** | AD-14 does not scope the one region to outcome messages. It says the region "carries save-failure, refetch-failure **and status messages**". "Loading your todos" is a status message. On a failed first load, the Loading status also speaks the **failure** text ("Couldn't load your todos. …"), which is plainly AD-14 content in a second region. The field-local over-limit region is defensible as inline field validation under AD-8. Better proposal: keep the over-limit region under AD-8 and drop the failure text from the Loading status. The List error panel is visible, and focus or the region can be left to it. Or ask Winston to amend AD-14 to allow exactly one hidden progress status. If Winston says no, this becomes a **critical** contradiction. |

## New findings

### High

- **[high]** **A refresh failure overwrites the mutation-failure message.** EXPERIENCE's Not-found row relies on AD-13 refetching after a *failed* mutation. When the network is down, that invalidation refetch fails at once. AD-11 sends the refresh failure to the announcer, and EXPERIENCE says "A new message replaces the current one". So "Couldn't mark “Pay rent” done…" is replaced almost immediately by "Couldn't refresh the list…". Two polite updates in quick succession also risk the screen reader dropping the first one. This breaks Flow 4 steps 2–4 and its climax ("one message that names the exact todo and why"). It also makes E6 ("a message explains the failure") flaky under `page.route` abort. (EXPERIENCE Component Patterns › Announcer, State Patterns › Refresh failed, Flow 4 ↔ AD-13, AD-11, AD-14, E6.) *Fix:* a UX priority rule within AD-14: a refresh failure never replaces an unacknowledged mutation-failure message (it is dropped or appended). Also flag for Winston: proposal that AD-13 invalidates after a failed mutation only for `not-found` (the helper has already reverted that todo, so no refetch is needed otherwise), or that AD-14's announcer API state the priority.
- **[high]** **Adding while the list is in its Error (or Loading) state, then failing, gives a false Empty state.** The add form stays usable in the Error state (an EXPERIENCE decision). The optimistic add seeds the absent cache, `[todo]`, so the List error panel disappears. The add fails, and the helper reverts that todo, leaving `[]`, so the Empty panel shows "No todos yet." The invalidation refetch fails too (still offline). AD-11 now forbids the error state because cached data exists. The user who was told "Couldn't load your todos" now sees "No todos yet". This breaks R9 ("each when its condition holds"), the Flow 4 failure path ("not an empty list") and K5. The same chain runs from the Loading state if the add fails. (EXPERIENCE State Patterns › Error, Add during first load; Component Patterns › Add form "enabled in every list state" ↔ AD-11, AD-13, R9.) *Fix:* flag for Winston. Proposal: define AD-11's "cached data" as data from a successful server fetch (for example, the query's `dataUpdatedAt` from a fetch, or a `loadedOnce` flag in the todos hooks). While none exists, the helper keeps optimistic adds in a separate pending list that renders above the skeletons or the List error panel, instead of seeding `['todos']`. UX change: add State rows for "Add during Error" and "Add fails before the first load succeeded".
- **[high]** **Network errors get their own wording, but AD-9 classes them as generic.** AD-9: "The client treats a non-2xx response without a problem body, **or a network error**, as a generic failure". AD-14 keys `messages.ts` by problem `type` and action "with a generic fallback". EXPERIENCE adds a `network` reason ("Check your connection and try again."), separate from the generic one. A builder would need a non-problem key that AD-9 doesn't define. AD-4 makes it worse: when the API is down, nginx answers with a problem, not a network error. When the host or tunnel is down, Cloudflare answers with HTML, so the generic reason applies. So Flow 3's "the server is unreachable… Check your connection" is the wrong copy. (EXPERIENCE Voice and Tone › Reasons, Flow 3 failure path, Flow 4 ↔ AD-9, AD-14, AD-4.) *Fix:* flag for Winston. Proposal: amend AD-9 and AD-14 to name `network` (fetch rejected or aborted) as a client-side failure kind in `messages.ts`, beside the generic fallback. AD-20 already separates "unreachable" (`abort`) from "failing". UX change: rewrite Flow 3's trigger as "the phone is offline", or show the server-unavailable reason.

### Medium

- **[medium]** **A failed create leaves its queued follow-ups undefined.** The UX lets the user edit, complete or delete an optimistic todo while its `POST` is pending: there is no indicator and nothing is disabled. AD-13 and U5 hold those requests until the create settles, but say nothing about what happens when it *fails*. If the queue is sent, `PATCH` returns `404`, and the UX override says "“{t}” was deleted elsewhere." That is false, and it replaces "Couldn't add". `DELETE` returns `404`, and "Deleted “{t}”." replaces "Couldn't add". (EXPERIENCE State Patterns › Not found, Delete 404, Add failed ↔ AD-13, U5.) *Fix:* flag for Winston. Proposal: when a create fails, the helper drops that todo's queued mutations silently. UX change: add a Row-state line saying that only "Couldn't add" is announced.
- **[medium]** **The revert flag depends on a signal the helper doesn't provide.** The 1.2s danger outline must appear on the card the helper just reverted. A failed delete re-mounts that card, which must mount already flagged. AD-13 lists only "revert and announce". AD-11 limits components to the hooks, and the wire `Todo` shape is fixed (AD-7). (DESIGN Todo card › Revert flag; EXPERIENCE Row states › Reverted ↔ AD-13, AD-11, AD-7.) *Fix:* flag for Winston, folded into flag 3. Proposal: the todos hooks expose `revertedAt(id)` (or an event), kept outside the `Todo` objects in the cache.
- **[medium]** **There is no retry policy for the query.** "No automatic retry (AD-13 spirit)" stretches AD-13, which binds the mutation helper only. TanStack retries a failed query three times by default, with backoff. So the List error panel and the refresh failure would arrive about 7s late, and every window-focus refetch adds more retries. (EXPERIENCE Component Patterns › Try again; State Patterns › Error, Refresh failed ↔ AD-11, AD-13.) *Fix:* flag for Winston. Proposal: AD-11 states `retry: false` for `['todos']` and fixes `refetchOnWindowFocus`. Without that, the UX's timing is undefined.
- **[medium]** **The problem type nginx emits is unspecified, so the UX's `storage-unavailable` reason is nearly unreachable.** AD-6 lists no `503` on any todo route. `storage-unavailable` comes only from `/api/health`. nginx's 502/503/504 problem (AD-4) has no named `type`. So "The server isn't available right now." appears only if nginx happens to use that type. (EXPERIENCE Voice and Tone › Reasons ↔ AD-4, AD-6, AD-9.) *Fix:* flag for Winston. Proposal: AD-4 names `/problems/storage-unavailable`, or another member of the closed set, for nginx upstream failures.
- **[medium]** **C3: the UX asks for a hand-rolled presence layer and cache diffing.** These pieces all need custom React state, with no animation library:
  - leaving rows kept after they leave the cache, for delete, not-found refetches and rows that vanish while in edit
  - detecting that an editing row vanished on refetch, and announcing it
  - restoring a failed delete "in place" with its own motion
  - restoring a failed add only if the field is empty, with the cursor at the end

  (EXPERIENCE Row states › Leaving, Not found, Edit open-todo vanishes; Motion › Delete ↔ C3, AD-11.) *Fix:* UX change. Keep the exit animation only for a user-initiated delete. Refetch removals unmount at once, and focus follows the after-delete rule. Drop the "deleted elsewhere" announcement for an editing row that vanishes, or keep it only if the draft would otherwise be lost silently.
- **[medium]** **AD-19's CSP blocks data-URI icons.** `default-src 'self'` means `img-src 'self'`, so `data:` images are blocked. Vite inlines small assets used in CSS as data URIs by default (`assetsInlineLimit`). The over-limit warning triangle, the "!" icons and the tick would break in `test` and `prod` if they are built as CSS `url()` (they would work in dev, where nginx sends no CSP). (DESIGN Character counter, Inline error, Announcer, Completion check ↔ AD-19, Conventions › Styling.) *Fix:* UX change. DESIGN states that every icon is inline JSX SVG or a text glyph with `aria-hidden`, never a CSS `url()`.
- **[medium]** **The auto-growing field isn't achievable in CSS alone in every engine Playwright runs.** `field-sizing: content` is not supported everywhere. Firefox lacked it as of 2025, and a `rows` fallback does not grow. With "no inner scroll", long text would clip or scroll in such engines, which breaks DESIGN's "Long text" state and R8 parity under E7. (DESIGN Text field ↔ Conventions › Styling, ticket Boundaries › browsers.) *Fix:* UX change. Specify a small JS height-sync fallback (set the height from `scrollHeight` on input) when `CSS.supports('field-sizing','content')` is false. This stays within CSS Modules.
- **[medium]** **axe can run mid-animation.** AD-20 runs axe in every e2e test. A scan that lands during the add fade-in (opacity 0→1), the done-card transition, the 120 ms edit fade or the announcer's entry can report `color-contrast` failures on partly transparent text. Leaving rows also rely on `inert` to avoid `aria-hidden-focus`. (EXPERIENCE Motion ↔ AD-20, E8.) *Fix:* flag for Winston. Proposal: the Playwright config sets `reducedMotion: 'reduce'` (browser emulation, not an app flag, so it is allowed under AD-20) for axe scans, or scans wait for animations to finish. Keep one motion-on test without axe.
- **[medium]** **Dark mode is never audited automatically.** Playwright runs in the light scheme by default, so axe in every e2e test checks only the light tokens. R14's "automated audit reports no AA violations" would not cover half of the shipped colour pairs. (DESIGN Colors (`-dark` roles) ↔ AD-20, R14, E8.) *Fix:* flag for Winston. Proposal: AD-20 adds a `colorScheme: 'dark'` axe pass, as a second project or one spec per E1–E6 state.
- **[medium]** **C5: dark mode is a feature beyond R1–R22 without a dated ticket decision.** The decision exists only as an undated memlog line. Dark mode doubles the colour contract and its audit surface. (DESIGN frontmatter, Colors; EXPERIENCE Foundation › Colour mode ↔ C5.) *Fix:* record a dated user decision in the ticket's Notes (Sofia), or cut dark mode from v1.

### Low

- **[low]** **The leaving row contradicts two other UX rules.** "Motion never delays state… the DOM… change at once" and "exactly one of list / Empty panel" both clash with a row kept 200 ms after it leaves the cache, next to an Empty panel after the last delete. Under reduced motion, removal must not wait for `animationend`, which never fires. (EXPERIENCE Motion › Rules, IA region 5, Row states › Leaving ↔ AD-11.) *Fix:* UX change. State that leaving rows are the one DOM exception, that Empty renders only after the last leaving row unmounts, and that removal uses a timer that is 0 under reduced motion.
- **[low]** **The revert motion is described as a chain.** "The card eases back… *then* the revert flag pulses" is a chain, which DESIGN's Don'ts forbid. A re-entering card after a failed delete would also play the add-enter motion unless that is suppressed. (EXPERIENCE Motion › Revert ↔ DESIGN Do's and Don'ts.) *Fix:* UX change. Run them in parallel, and specify the re-entry motion for a failed delete.
- **[low]** **The optimistic text must match what the server stores.** The UX doesn't say that the optimistic card and the `POST`/`PATCH` body carry the *trimmed, newline-normalised* description. If they don't, the card text shifts when the refetch arrives, and an idempotent replay compares a different value. (EXPERIENCE Add form, Edit form ↔ AD-8, AD-6.) *Fix:* UX change. Add one line saying the client sends and renders the trimmed value.
- **[low]** **"Unchanged" has no comparison basis.** "Saving unchanged text sends nothing" doesn't say what it compares against: the trimmed draft against the text when edit opened, or against the current cache, which matters when a refetch changed it elsewhere. (EXPERIENCE Edit form ↔ AD-8 "send only the fields it is changing".) *Fix:* UX change. Compare the trimmed draft with the current cached description.
- **[low]** **The `conflict` wording is wrong.** The only `409` is a `POST` that reuses an `id` with different content. Nothing is "a change made elsewhere". (EXPERIENCE Reasons › conflict ↔ AD-6.) *Fix:* UX change. Use the generic reason for `conflict`.
- **[low]** **Rapid adds can reorder after a refetch.** AD-13 orders requests per todo only, so two adds' `POST`s can arrive in either order. The server's `createdAt` (or, on a same-ms tie, the random `id`) can then reorder the cards after the refetch, with no motion specified. (EXPERIENCE Todo list ↔ AD-6, AD-11, AD-13.) *Fix:* UX change. Accept the reorder and state it, or animate nothing.
- **[low]** **C4 measurement.** Enter animations start at opacity 0 and `0fr`. With the given ease-out, about 85–90% of the change is visible at 100 ms, which is probably fine. The performance report should still define "shows" as the first painted frame of the change, not the end of the animation. (DESIGN motion; EXPERIENCE Motion ↔ C4, R19.) *Fix:* note this for the R19 report. No UX change needed.
- **[low]** **The Key Flows don't cite AD-20 scenario ids.** They don't map to E1–E8, and the Surface closure table omits R11 and R12 even though Flows 3 and 4 serve them. (EXPERIENCE IA › Surface closure, Key Flows ↔ AD-20, test-strategy.) *Fix:* UX change. Tag each flow and failure path with its E id (Flow 1 → E1–E5, E7; Flow 2 → E8; Flow 3 → E1, E6; Flow 4 → E6). Add R11 and R12 rows.
- **[low]** **The Try again citation is stretched.** "AD-13 spirit" cites a mutation-helper AD for a query behaviour. (EXPERIENCE Component Patterns › Try again ↔ AD-13.) *Fix:* UX change. Cite AD-11 once Winston settles the query retry policy (medium finding above).
- **[low]** **Wording outside the announcer.** The vanished-in-edit and not-found messages, and the List error panel text, are fine under AD-14 only if they also come from `messages.ts`. EXPERIENCE says "All runtime strings live in one `messages.ts`". `messages.ts` must also key a status that is neither a problem type nor an action ("deleted elsewhere" on a refetch). (EXPERIENCE Voice and Tone ↔ AD-14.) *Fix:* UX change. List the `status.deletedElsewhere` and `status.deleted` keys explicitly.
- **[low]** **The AD-19 check found nothing to fix.** Todo text appears only through React text and `aria-label` (escaped). Problem `detail` is never shown, and the client does no logging. *Fix:* none. This is listed for completeness.
