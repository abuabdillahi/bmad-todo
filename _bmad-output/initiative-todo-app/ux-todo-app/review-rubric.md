# Spine Pair Review — BMad Todos

## Overall verdict
The pair is close to a clean build contract. All 74 colour tokens are hex with complete light/dark pairs, every `{token}` reference in both files resolves, every recomputed contrast figure matches the table, component names line up one-to-one across both spines, and every memlog decision is carried through, including the late changes to not-found handling and the storage-unavailable wording. What remains is mostly about the Announcer's position in the page flow. It can be off-screen when a failure happens below the fold, and a late delete-success banner shifts the list under the user's finger when delete can't be undone. Each needs a committed rule before UI stories start. The medium findings are local fixes: one uncovered contrast pair, one flow climax that contradicts the replacement rule, a motion rule that forbids the approved motion, and three state gaps.

## 1. Flow coverage — adequate
Checked: the ticket's UX-facing Requirements (R1–R9, R11–R14; R10 and R15–R22 are API, infra or delivery) against the Surface closure table and the four Key Flows. Each flow has a named protagonist, numbered steps, a bolded climax and a failure path. Every UX requirement is exercised by at least one flow, and the ticket's Done-when (unguided on phone and desktop, persistence across sessions) is covered by Flows 1–3. Step-level checks pass: Flow 2's tab sequence matches the IA tab-stop table, "10/200" matches "Buy stamps", and the Flow 4 message strings are exactly lead plus reason.

### Findings
- **medium** Flow 4's climax ("Jun reads one message that names the exact todo and why… nothing was lost silently") contradicts the committed rule that a new message replaces the current one. After step 5 the banner holds only the `refresh` message, which names no todo. The complete and delete failures from steps 2–3 were overwritten, and their 1.2s revert flags are long gone. Because e2e scenarios are derived from flows, a test written from this climax would assert something the spec forbids (EXPERIENCE.md, Key Flows › Flow 4, steps 5–6; Component Patterns › Announcer). *Fix:* rewrite the climax to what actually holds: the list never vanished, each failure was announced when it happened, and the latest message is on screen. Alternatively, decide explicitly that a `refresh` failure must not replace a pending mutation-failure message.
- **medium** Focus moves to the Text field (add) after Dismiss, after Try again and after deleting the last todo. On a phone, focusing a textarea from a tap handler opens the soft keyboard, which covers half the screen when the user only meant to close a banner. Flow 1 step 9 (phone, deletes the last todo) and Flow 4 step 7 (phone, taps Dismiss) both trigger it, but neither flow mentions it (EXPERIENCE.md, Interaction Primitives › Focus management rows Delete, Dismiss, Try again). *Fix:* choose a target that doesn't open the keyboard, such as the first Completion check, the list, or `<main>`/`<h1>` with `tabindex="-1"`, or state that the keyboard opening is accepted. Then reflect the result in Flows 1 and 4.
- **low** Flow 3's failure path says "the server is unreachable" and shows the `network` reason ("Check your connection…"). That only holds when the whole origin is unreachable (the AD-20 `abort` injection). If the API container is down, nginx answers with an RFC 9457 problem (AD-4), and the Reasons table doesn't say which reason that problem maps to (EXPERIENCE.md, Key Flows › Flow 3 failure; Voice and Tone › Reasons). *Fix:* say "the connection drops" in Flow 3, and state which reason an nginx 502/503/504 problem gets. If its `type` is unknown, add it to the Winston flags.
- **low** R14 requires a manual keyboard and screen-reader pass of every core action, but Flow 2 never reopens a todo. No flow walks a failed edit save, the one revert whose message differs most ("…is back as it was") (EXPERIENCE.md, Key Flows › Flow 2, Flow 4). *Fix:* add "Space again: not checked" to Flow 2 step 3, and an edit failure step to Flow 4.

## 2. Token completeness — adequate
Checked: all frontmatter groups (colors 74 = 37 roles × light/dark, typography 12, rounded 5, spacing 10, motion 11 as a declared extension, components 29). 60 distinct `{path}` references in DESIGN.md and 16 in EXPERIENCE.md all resolve. Every colour value is a 6-digit hex, and no role lacks its `-dark` twin. All 23 load-bearing pairs and all 7 hover/pressed rows were recomputed from the hex values, and each matches the table to two decimals. The token-to-CSS custom property rule is explicit and covers every group. This is nearly strong. One load-bearing combination is missing.

### Findings
- **medium** A completed todo in edit mode takes the **active** card treatment ([ASSUMPTION], "so the field and buttons keep their verified contrast"), but its Completion check stays checked. The checked edge `border-done-check-dark` (#666B8A) on `surface-card-dark` (#22253A) is **2.90:1**, under the 3:1 target for the checkbox boundary that DESIGN.md itself sets. The checked fill against the card is 1.10. Light mode passes at 3.61. Flow 2 reaches this state directly: it checks "Send invoice", then edits it. axe won't catch non-text contrast, so it would surface only in the manual R14 pass (DESIGN.md, Components › Todo card › Edit; Colors › Contrast table has no `border-done-check` on `surface-card` row). *Fix:* add the pair to the table and either lighten `border-done-check-dark` to at least 3:1 on both `surface-page-dark` and `surface-card-dark`, or use `border-check` for the checked edge while in edit mode.
- **medium** The Do's and Don'ts ban hard-coded px in component CSS ("Read every value from tokens… Don't hard-code hex, px or ms"), yet several values exist only in prose with no token: optical offsets (−9px check margins, 1px text top padding, 7px wide-layout nudge, −2px edit-mode nudge), the announcer icon glyph (14px/800, 4px nudge), the inline-error glyph (12px/800), the warning-triangle stroke (1.8), and the Done chip's 1px raise. A builder must either break the rule or invent token names, and three builders will invent three different sets (DESIGN.md, Layout & Spacing › Optical offsets; Components › Announcer, Inline error, Character counter, Done chip; Do's and Don'ts row 8). *Fix:* add these to the relevant `components.*` entries (e.g. `completion-check.margin: -9px`, `todo-card.text-nudge-wide: 7px`), or narrow the Don't to say that optical nudges listed in prose may be literal.
- **low** Two token definitions are ambiguous. `components.text-field.min-height: 32px` conflicts with the prose "Rest: … 59px for the add field including the counter", and nothing says which element the 32px applies to. `announcer-status` defines only fill, text and edge, while its Dismiss "takes the Cancel button's soft style" with no token entry (DESIGN.md frontmatter `text-field`, `announcer-status`; Components › Text field, Dismiss button). *Fix:* rename to `textarea-min-height` or state the element, and add a `dismiss-button-status` entry that references the `cancel-button` tokens.

## 3. Component coverage — strong

DESIGN.md Components and EXPERIENCE.md Component Patterns carry the same 23 names: Focus ring, Page heading, Announcer, Dismiss button, Add form, Text field, Character counter, Inline error, Add button, Todo list, Todo card, Completion check, Done chip, Edit form, Edit, Delete, Save and Cancel buttons, Empty panel, Skeleton card, Loading status, List error panel and Try again button. Each has a real visual spec and real behavioural rules. Revert flag is a Todo card state in both files, and it also has its own frontmatter token block.

### Findings
- **low** The Completion check's states list hover and pressed only for the unchecked circle. Checked + hover and checked + pressed are undefined, though a done card's check is just as clickable (DESIGN.md, Components › Completion check). *Fix:* state whether the checked circle's edge and fill step on hover and press, and add the resulting pairs to the hover/pressed table.
- **low** The field-local, visually hidden polite region that voices "over the character limit" is a real DOM element with its own rules, but it has no component name in either spine. Loading status was given a DESIGN.md entry "so both spines name it", and this region wasn't (EXPERIENCE.md, Component Patterns › Character counter; FLAG 5). *Fix:* name it (e.g. "Limit status") in both spines, the same way Loading status is named.

## 4. State coverage — adequate
Checked: the one IA surface, region by region. List area: loading, populated, empty, error, refresh-failed, refetching, add during first load. Rows: active, done, saving, edit, invalid, over-limit, reverted, not-found, leaving, delete 404, delete success, and edit open while the todo vanishes or changes on refetch. Add form: rest, typing, over-limit, empty submit, submitted, add failed. Announcer: empty, failure, success, replaced, dismissed. Focus, reduced motion and offline (per-action network failure; offline mode out of scope) are covered, and permission-denied doesn't apply. The inventory is unusually complete. The gaps are about where the Announcer sits in the page flow.

### Findings
- **high** The Announcer sits in normal flow above the add form, with "no… sticky bars", and it never moves focus. On a list longer than one screen, a failure on a card below the fold is explained in a banner the user can't see. The only on-screen cue is a revert flag that lasts 1.2s. That is exactly what AD-14 exists to prevent ("failures a sighted user never sees"), and it undercuts R7's "a message says so" (EXPERIENCE.md, Component Patterns › Announcer; Interaction Primitives › Focus management, "Announcer message appears: Not moved"; DESIGN.md, Elevation & Depth). *Fix:* commit a rule for an out-of-view Announcer. Options include making it sticky to the viewport top while it holds a message (with a matching Elevation exception), scrolling it into view without moving focus, or adding a persistent per-card marker until the next message. Then add a state row for it.
- **high** Delete success is announced "on server confirmation, not on press" ([ASSUMPTION]), so the banner appears roughly 100–300ms after the tap and pushes the add form and the whole list down by its height (about 130px on a phone, with Dismiss stacked). That happens while the deleted card is collapsing and the cards below move up. A user deleting several todos in a row on a phone can land the next tap on a different card's Delete. Delete is immediate with no undo (R5), so the mis-tap destroys data. Nothing in State Patterns or Motion addresses the layout shift (EXPERIENCE.md, State Patterns › Delete succeeded; Motion › Announcer in; DESIGN.md, Brand & Style "never between the user and the result"). *Fix:* commit a no-shift rule. Options include announcing delete success optimistically on press, so the banner's growth coincides with the collapse; holding the banner's slot open once shown until Dismiss; or ignoring pointer-down on list buttons for the duration of a shift. Then state it in Motion › Rules.
- **medium** The visual for "Add during first load" is undefined. The IA says the list area shows **exactly one** of the list, Empty panel, skeleton list or List error panel, and the State Patterns row only says the list "must not look emptied". FLAG 4 asks Winston about the data path, but which blocks render (new card above the skeletons? skeletons kept until the load resolves?) is a UX decision the builder still needs (EXPERIENCE.md, IA › Regions row 5; State Patterns › Add during first load). *Fix:* specify the render, e.g. "the optimistic card renders at the top of the skeleton list, and skeletons stay with `aria-busy` until the first load settles", and relax "exactly one" to allow it.
- **medium** Replacing an Announcer message with identical text, such as the same complete failure twice in a row, changes nothing in the live region. Screen readers won't re-announce it, and sighted users see no change apart from the brief flag. That's a known live-region pitfall, and nothing tells the builder to handle it (EXPERIENCE.md, Component Patterns › Announcer; State Patterns › Announcer states). *Fix:* add a rule that a repeated message is re-announced, for example by clearing the region for one frame before setting it or by keying the text node per message, and that the banner gives a visual cue.
- **low** Deleting the last todo leaves the order of events unspecified. The leaving row stays rendered for `{motion.duration-base}` after it leaves the cache, but the list area may show only one block, so it's open whether the Empty panel appears at once beneath the collapsing card or after it unmounts (EXPERIENCE.md, State Patterns › Leaving and Empty; Key Flows › Flow 1 step 9). *Fix:* state the order, e.g. "Empty panel fades in after the leaving row unmounts".
- **low** The text field's fallback is `field-sizing: content` with a `rows` fallback. A `rows` fallback doesn't grow, so in any default Playwright browser that lacks `field-sizing`, long text scrolls inside the field, against "no inner scroll" (a user decision) (DESIGN.md, Components › Text field; EXPERIENCE.md, Component Patterns › Text field). *Fix:* confirm support across Chromium, Firefox and WebKit at the pinned Playwright version, or specify a JS auto-size fallback.

## 6. Bloat & overspecification — adequate
Checked: pixel restatement, ticket restatement, prose versus tables, sections no consumer would read, and decorative narrative. Both files are mostly tables with short rules. The Surface closure table maps requirements without restating them, and DESIGN.md's editorial prose is brief and tied to decisions (recede, withdrawal, the v2 reset failure as rationale for a Do). The main issue is one over-tight rule.

### Findings
- **medium** The motion rule is stricter than the approved motion. DESIGN.md Do's say "Animate only opacity, transform and grid-row height", and Brand & Style says "opacity, transform and height only". But the approved Complete motion (m2) eases the card from filled to hollow (background-color, border-color), fills the circle and draws the tick (`stroke-dashoffset`). The revert flag pulses an outline, and the revert eases colours back. A builder can't satisfy both (DESIGN.md, Brand & Style ¶3; Do's and Don'ts last row; EXPERIENCE.md, Motion › Complete, Revert). *Fix:* reword the rule to "no layout properties except grid-row height; colour, opacity, transform and `stroke-dashoffset` may transition", and keep the ban on animating width, height, top or margin directly.
- **low** Internal render labels and history appear where downstream readers can't resolve them: "m5b" (Motion table), "m5a, m5c, P1, v4 cross-fade" and "quiet paper, ledger mono, bold block" (Inspiration), "FLAG 2…5" as bare references, and "An early dark rendering… the user rejected it" (DESIGN.md Brand & Style). They only make sense next to `.memlog.md` and `.working/` (EXPERIENCE.md, Motion; Inspiration & Anti-patterns). *Fix:* drop the labels, or define them once in words (e.g. "instant swap with a fade-in" instead of m5b), and point FLAG n to the Architecture flags table row.
- **low** Responsive behaviour is stated in full in both spines (DESIGN.md › Layout & Spacing › Responsive rules; EXPERIENCE.md › Responsive & Platform): target heights, Dismiss placement and inline versus stacked actions. Two copies of the same rule will drift. *Fix:* keep geometry in DESIGN.md and only the behavioural invariants ("no action at only one width", browsers) in EXPERIENCE.md, with a pointer.

## Mechanical notes
- **Frontmatter.** DESIGN.md has name, description, status (draft), created, updated, sources and all token groups. EXPERIENCE.md has name, status, created, updated and sources. Both `sources` lists resolve. The UX index `ux-todo-app.md` links both spines and the ticket.

- **Colour pairs.** 37 roles, each with a `-dark` twin, all `#RRGGBB`. The counts match the memlog distillation record (colors 74, typography 12, rounded 5, spacing 10, motion 11, components 29).
- **Contrast recomputation.** All 30 stated ratios (23 load-bearing pairs and 7 hover/pressed rows) reproduce exactly from the hex values. The one uncovered load-bearing pair found is `border-done-check-dark` on `surface-card-dark`, at 2.90 (see 2).
- **Name consistency.** Component names are identical across DESIGN.md Components, EXPERIENCE.md Component Patterns, the IA table, State Patterns and Key Flows. Minor casing variants ("skeleton list" for the `<ul>` holding Skeleton cards, "revert flag" lowercase) are used consistently in both files.
- **Unresolvable internal labels.** "v2", "v4", "v5", "m5a/b/c", "P1" and "FLAG n" refer to memlog and `.working/` artifacts (see 6).
- **Mermaid.** Neither spine contains Mermaid, so there is nothing to validate.
- **Line counts.** DESIGN.md is 599 lines and EXPERIENCE.md is 406 lines. The memlog's distillation entry records 409 for EXPERIENCE.md, which predates the later not-found and storage-unavailable edits. This is not a defect.
