# Accessibility review

## Verdict

The update holds up. I found no AA failure in the spec as written, and every fix from the earlier review still stands: live regions are mounted empty, repeats are cleared and set again, focus is handed off first, and no timers are used. The remaining risk sits in what happens **without** a user action: focus moved by a refetch, list changes nobody announces, and the replace-as-you-type rule. Any of these could ship as a lost-focus bug or a misleading screen-reader experience if built literally. All of them can be fixed inside AD-11, AD-13 and AD-14, or documented as accepted.

## Findings

**[medium]** Automatic recovery lands focus on an actionable checkbox, and the user still doesn't hear what loaded (§ Interaction Primitives › Focus management, line 291; WCAG 2.4.3, 3.2.2). The row says: "The first todo's Completion check, so the user hears what loaded." The common case is a screen-reader user who tabbed back to Try again and is waiting for the Wi-Fi. A reconnect refetch succeeds, the panel is replaced, and focus jumps to "Pay rent, checkbox, not checked". The user only hears one todo's name and state, not that the list loaded or how many items it has. If they press Space or Enter at that moment, expecting Try again (NVDA in browse mode clicks on Enter), they toggle a todo they never chose. When the list is empty, the heading target says "BMad Todos, heading level 1", not "No todos yet." *Fix:* Change the target to the list area element that just rendered. That is the Todo list `<ul role="list" aria-label="Todos" tabindex="-1">`, which NVDA, JAWS and VoiceOver read as "Todos, list, 3 items", or the Empty panel `<p tabindex="-1">`, which reads "No todos yet.". Neither is a tab stop or actionable, and neither opens the phone keyboard, so the touch-versus-keyboard question goes away. Tab then reaches the first Completion check. Add both elements to the focus-ring rule (DESIGN.md Components › Focus ring already covers "every focusable element").

**[medium]** Recovery and a successful Try again are silent for anyone whose focus is outside the panel (§ Component Patterns › Loading status, line 192; § State Patterns › List states "Error, recovered without Try again", line 210; Flow 3 failure path, line 422; WCAG 4.1.3, 1.3.1). The Loading status voiced "Couldn't load your todos. Check your connection and try again." In the Flow 3 path, "focus stays in the add field". The reconnect refetch then replaces the panel "with no skeletons in between and no message", and the Loading status "is silent once the list is loaded". A sighted user sees the red panel turn into the list. A screen-reader user's last spoken state is still the error, so they keep believing the list is down, and may keep adding into what they think is a broken app. Try again is similar: the user hears "Loading your todos", and then nothing when it succeeds. Strictly this is not a 4.1.3 failure, because the list is content and not a status message, but the visual and spoken states disagree. AD-14 leaves no live route for it: the Loading status "speaks only while the list is not loaded", and none of the three Announcer callers owns a load success. *Fix:* Record it as an accepted gap. Add it to Open Items as an **[ASSUMPTION]**: "Recovery from the List error panel, by Try again or by an automatic refetch, is not spoken (AD-14 has no route); focus moves only if it was in the panel." Add it to the Accessibility Floor's manual-pass expectations, so a tester doesn't log it as a bug. If the user won't accept the gap, the only fix is a new flag for Winston, a one-time utterance by the Loading status at the not-loaded → loaded transition. So "New flags from this update: none" would then change.

**[medium]** "Landed after all" leaves a false failure message on screen, and screen-reader users are the ones who will resubmit (§ State Patterns › Row states "Landed after all", line 238; Flow 4 step 7, line 436; WCAG 4.1.3, 3.3.4). Take Jun's case if the add had landed. The banner keeps "Couldn't add “Call landlord”. Check your connection and try again.", the field still holds the restored "Call landlord", and the refetch silently puts "Call landlord" into the list. A sighted user may notice the new card. A screen-reader user in the add field hears nothing, trusts the failure message, presses Enter, and creates the duplicate. The completion case contradicts itself in the same way: the banner says "so it's still open" while the checkbox is now checked. *Fix (inside AD-13, through the per-call promise):* The Add form already knows the id of its own failed call. If that id later appears in the `['todos']` cache and the field still holds exactly the restored text, clear the field back to "0/200" without moving focus. This removes the duplicate path for everyone. In Open Items, extend the "Landed after all" row with the screen-reader impact: "the failure message is not retracted, and no screen-reader cue marks the reconcile".

**[medium]** Refetch-driven focus moves are underspecified in four ways that can lose or steal focus (§ Focus management, lines 288 and 291; § Hand-off order, line 298; WCAG 2.4.3).
- *Detection.* Once the commit has removed the focused element, the layout effect can no longer test `panel.contains(document.activeElement)`: the panel is detached and `activeElement` is already `<body>`. A literal build therefore never fires, and focus drops to `<body>`. A build that instead tests "activeElement is body" fires falsely after a touch user's tap on blank page area, and pulls focus into the list.
- *Inert rows.* "The first todo" or "the next todo" can be a Leaving row, which is `inert`. Calling `focus()` on it fails and focus drops to `<body>`.
- *No activation.* Line 288 reuses the after-delete rule, which ends in "the add field or heading". After a refetch no activation exists to choose between the two, and line 291 settles the same question with the heading. The two rows disagree.
- *Order.* For the edit-mode removal, the spec doesn't say whether focus moves before or after the "deleted elsewhere" announcement in that commit.

*Fix:* Add to Hand-off order:
- "Whether focus is inside the row or panel is recorded before the removing commit (a `focusin`/`focusout`-tracked flag on the row and on the List error panel). The layout effect moves focus only if that flag was set and `activeElement` is now `<body>`."
- "Focus targets skip Leaving rows."
- "When the after-delete rule runs with no user activation, an empty list sends focus to the Page heading."
- "Focus moves before `announce` is called."

Extend the component test to cover both sides: focus elsewhere stays put, and focus inside lands on the target.

**[medium]** Optimistic rows must keep their identity when the list becomes loaded (§ Information Architecture › List area exceptions, line 39; § List states "Add during Loading" and "Error, recovered without Try again", lines 210 and 214; WCAG 2.4.3, 3.3.7). While the list is not loaded, optimistic adds render "in a Todo list above the skeleton list or List error panel". Once loaded, the list area renders the cache instead. Suppose that pre-load list and the loaded list are different subtrees, or rows change `key` or parent. A user who added during a slow first load, then tabbed to the new card's checkbox or opened its Edit form, has the row remounted under them when the load succeeds. Focus drops to `<body>`, and the in-progress edit draft is gone. No focus row covers this, because the row is not "removed". *Fix:* Add to Component Patterns › Todo list: "The same `<ul>` and the same row `key` (the todo id) are used before and after the first successful load, so focus, an open Edit form, and an open Delete confirm survive the transition." Add a component test that keeps focus in an optimistic card's Text field (edit) across the first successful load.

**[medium]** Replacing characters "as it enters the field, typed or pasted" can break caret position and undo, and the word "typed" invites a Tab trap (§ Component Patterns › Text field, line 159; Character counter, line 161; WCAG 2.1.2, 3.3.2).
- *Tab trap.* "Every character … (`\p{Cc}`, including line breaks and tabs) … becomes a space as it enters the field, typed or pasted." The Tab key never types a tab into a textarea; it moves focus. A developer who reads "typed tabs" as an instruction to handle `keydown` Tab and insert a space creates a keyboard trap.
- *Caret.* If the replacement runs on `input` by writing a new value back into the controlled field, the caret jumps to the end after a mid-text paste. Screen-reader and magnifier users then type in the wrong place without knowing it.
- *Undo.* Chrome drops the undo history on a programmatic value change, so Ctrl+Z can't undo the paste.
- *IME.* Rewriting the value during a composition breaks the IME.
- *Wording.* "So the field and the counter show exactly what will be saved" is not quite true. The field still shows leading and trailing spaces, but the counter excludes them, so typing leading spaces leaves it at "0/200".

*Fix:* Reword it: "Tab is never intercepted and always moves focus. Forbidden characters arriving by paste, drop, autofill, or dictation are replaced: in `beforeinput` for `insertFromPaste`/`insertFromDrop`, by cancelling and inserting the cleaned text through the editing API so undo stays one step; otherwise on `input`, by restoring `selectionStart`/`selectionEnd`, which is safe because each replacement is one-for-one. The value is never rewritten while `isComposing`." Change "exactly what will be saved" to "what will be saved, apart from leading and trailing spaces, which the counter already excludes". Add a K1 case for a mid-text paste that checks the caret position and Ctrl+Z.

**[medium]** "Deleted elsewhere" after a 404 can be cut off by the focus move one round trip later, and can be spoken twice (§ Row states "Not found", line 230; Focus management, line 288; Overrides, line 98; Completion check, line 173; WCAG 4.1.3).
- *Cut off.* A user toggles a todo that someone else deleted. The helper announces "“Buy milk” was deleted elsewhere.", and the refetch removes the row a round trip later. Focus is on its checkbox, so the after-delete rule moves focus in the layout effect. NVDA and JAWS cut off speech when focus moves, so the message is chopped mid-sentence and replaced by "Pay rent, checkbox, not checked".
- *Spoken twice.* The checkbox "stays operable during edit mode". A 404 on complete while the row is in edit mode makes the helper announce "deleted elsewhere". The refetch then removes a row in edit mode, so the list area announces the identical text, which is "cleared and set again" and spoken twice.

*Fix:* Let the row react to its call's promise (AD-13 permits local reactions). On `failed` with kind `not-found`, if focus is inside the row, apply the after-delete rule then, in the same task as the helper's announcement, instead of after the later refetch. Add to the "Edit open, todo vanishes on refetch" row: "skipped if the current undismissed message is already “{t}” was deleted elsewhere for this todo."

**[low]** The Loading status's timers need to be reset on each state entry (§ Component Patterns › Loading status, line 192; WCAG 4.1.3). Because it now speaks on every entry, overlapping timers become possible. Suppose an error is spoken at t=0, Try again is pressed at t=4.9 s, and the fetch fails fast. The old 5 s clear can empty the new error text before it is spoken. Also, no rule clears the previous error text when loading is entered, so the stale "Couldn't load…" sits in the status under the skeletons for browse mode. *Fix:* Add "Each entry into loading or error empties the status and cancels any pending 500 ms or 5 s timer before starting its own."

**[low]** Announcer repeats and replacements (§ Component Patterns › Announcer › Replacement, line 152; WCAG 4.1.3).
- *Refresh repeats.* While offline with the list loaded, every window focus and reconnect runs a refetch that fails. Each time, the identical refresh message is "cleared and set again", so a user switching windows hears the full sentence on every return.
- *Status over failure.* "A `status` message does replace a failure." That is AD-mandated, but if "Added" arrives right after a failure, the failure can be replaced before a polite screen reader has spoken it, and sighted users lose it too.

*Fix:* For kind `refresh` only, an identical message that is still showing is left as it is, with no clear-and-set. Note the status-over-failure case as accepted in the Accessibility Floor's manual-pass expectations.

## Checked and fine

- The Loading status speaks on Try again and on a failed Try again. The 500 ms delay keeps a fast offline failure down to the error line, and a background fetch that fails while in error is error → error, not an entry, so it stays silent.
- Try again while a save is pending is not a trap. The add form and the optimistic cards stay operable, the skeleton stops breathing at 4.8 s (2.2.2), "Loading your todos" is spoken once, and focus has already moved off the removed button.
- A `refresh` never replaces an undismissed `failure`, and "deleted elsewhere" is kind `failure`, so the message about a lost draft can't be overwritten by a background failure.
- Focus is not moved when the panel is replaced while focus is elsewhere. Nothing is stolen from the add field (Flow 3).
- Recovery swaps the panel for the list with no skeleton flash, so there is no extra busy state or motion.
- An empty-list recovery target that never opens the phone keyboard respects the touch rule.
- The rule of moving focus in a layout effect before paint is sound, provided detection is fixed as above, and a component test is required.
- The counter counts after the replace and the trim, the same value as the request body (AD-8). The control-character rejection is unreachable, so there is no unexplained server-only error.
- Add during Loading: the cancelled first-load fetch is neither a failure nor spoken, so there is no false error.
- An add that fails before the first load never shows "No todos yet." The panel or the skeletons remain.
- "Added" and "Deleted" are announced by the helper, so they survive the card unmounting. The failed-edit draft map is owned by the list area, so 3.3.7 holds even when the card unmounts.
- A restored row after a failed delete mounts fresh, without `inert` or `aria-hidden`, and keeps its revert flag.
