- (event) initiative created from prd-todo-app.md (pasted PRD, 2026-11-23)
- (requirement) R1 (prd ¶2): a user creates a todo by entering a short text description; it appears in the list
- (requirement) R2 (prd ¶2): every todo carries its description, a completion status, and its creation time
- (requirement) R3 (prd ¶2): opening the app shows the user's todo list straight away, with no onboarding or explanation
- (requirement) R4 (prd ¶2): a user marks a todo complete and can return it to active
- (requirement) R5 (prd ¶2): a user deletes a todo; it leaves the list and does not come back on refresh
- (requirement) R6 (prd ¶3): completed todos look visibly different from active ones at a glance
- (requirement) R7 (prd ¶3, ¶5): add, complete and delete show in the list immediately, without waiting on the server; a failed save reverts the change and says so
- (requirement) R8 (prd ¶3): every action works on desktop and mobile screen widths
- (requirement) R9 (prd ¶3): the list shows a distinct empty state, loading state, and error state, each when its condition holds
- (requirement) R10 (prd ¶4): a backend API creates, lists, updates and deletes todos
- (requirement) R11 (prd ¶4, ¶7): todos and their status survive a page refresh, a new browser session, and a server restart
- (requirement) R12 (prd ¶4, ¶5): the API rejects invalid input with a clear error and never leaves a todo half-written; the client shows failures without losing the list or blocking further use
- (constraint) C1 (prd ¶4): no authentication or multi-user in v1, but the data model and API must allow adding an owner to todos and auth later without a rewrite
- (constraint) C2 (prd ¶1, ¶4): full-stack: a frontend client backed by a server API with durable server-side storage; browser-only storage does not meet R11
- (constraint) C3 (prd ¶1, ¶5): favour simplicity and maintainability: the fewest moving parts, easy for a new developer to understand, run, deploy and extend
- (constraint) C4 (prd ¶5): interactions feel instantaneous under normal conditions
- (constraint) C5 (prd ¶1, ¶6): v1 scope is the core loop only; no feature beyond R1-R12 without a dated decision
- (assumption) completion is a toggle: a completed todo can be returned to active (prd ¶2 says only completion)
- (assumption) editing a todo's text is out of v1: prd ¶2 lists create, view, complete, delete; update in CRUD covers completion
- (assumption) a description is required (non-empty after trimming) and capped at 200 characters to keep it short
- (assumption) the list is ordered by creation time, newest first
- (assumption) delete is immediate, with no confirmation dialog and no undo
- (assumption) instantaneous (C4) means the UI reflects an action within 100 ms and the API answers within 300 ms at p95 under single-user load
- (question) with no accounts, every visitor to a deployment shares one list: is that acceptable for v1, or must the deployment be private? (waits: platform/deploy epic)
- (question) stack and production deployment target are not stated in the PRD (waits: architecture, opening epic)
- (question) accessibility is not stated: is keyboard use and screen-reader labelling in scope for v1? (waits: UI epic)
