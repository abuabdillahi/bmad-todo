# Reconcile: amended architecture spine vs the UX experience spine

## Verdict

**Every flag is decided. 6 match the UX proposal and 4 differ, so EXPERIENCE.md now needs text edits. No change is needed on the architecture side for the inline delete confirm.** All 3 high and all 4 architecture-side medium findings in review-spine-consistency.md are now covered by a spine rule. The amendments leave 4 behaviours that EXPERIENCE depends on unstated or ambiguous, mostly about fetch cancellation and when a fetch may start. There is also 1 wording gap in AD-14. This review does not re-argue any decision.

## Other gaps: EXPERIENCE depends on spine behaviour that is contradicted or unstated

1. **[medium] A fetch the helper cancels is not classified.** AD-13 cancels in-flight `['todos']` fetches before every mutation, "before the first load, too". AD-11 records *last fetch failed* "from the query function". AD-9 classes any rejected `fetch` as `network`. A cancelled fetch rejects. Read literally, then, an add during Loading would flip the list to the Error panel. The Loading status would then speak "Couldn't load your todos. Check your connection…". This contradicts EXPERIENCE State Patterns › **Add during Loading** ("The skeletons and Loading status stay until the first load settles"). The spine also never says a cancelled refetch is not a `refresh` failure. EXPERIENCE's network reason defines `network` as "rejected **or aborted**", which strengthens the wrong reading. *Needed in the spine:* AD-11 (or AD-9) should say that a fetch the helper cancels is neither a success nor a failure, and leaves *loaded* and *last fetch failed* unchanged. *Needed in EXPERIENCE:* drop "or aborted", or limit it to aborts the app did not start.

2. **[medium] Fetch timing in the Error state is now partly undefined.**
   - AD-11 defers Try again while any todo mutation is pending. EXPERIENCE Component Patterns › Try again promises "The panel is replaced by skeletons at once". Its own "Add during Error" row creates exactly that pending window.
   - AD-11 does not say whether a fetch in flight while the list is not loaded counts as Loading or as Error, that is, whether *last fetch failed* clears when a fetch starts. EXPERIENCE's "skeletons at once" needs it cleared.
   - AD-11 turns on refetch on focus and on reconnect. That means the Error panel can be replaced without Try again. EXPERIENCE does not describe this. Flow 3's failure path has the user press Try again after Wi-Fi returns, although the reconnect refetch would already have run. Focus management has no row for the panel being removed by an automatic refetch while focus is on Try again. The hand-off order lists only a Try again press, so focus can drop to `<body>`.
   
   *Needed:* the spine should state when *last fetch failed* resets. EXPERIENCE should then define what Try again shows while a fetch is deferred, and where focus goes when an automatic refetch removes the panel.

3. **[medium] The "deleted elsewhere" message for an editing row has no owner and no kind.** EXPERIENCE State Patterns › **Edit open, todo vanishes on refetch** has the Announcer say "“{t}” was deleted elsewhere". This is not a mutation outcome. AD-13 says "The helper, not a component, owns every announcement". AD-14 lists only mutation-failure, refresh-failure and mutation-status messages, so no `kind` covers it. As `status`, it would replace an undismissed failure. As `failure`, it would block refreshes. EXPERIENCE Component Patterns › Announcer › Messages ("failures every time, and two status messages") doesn't list it either. *Needed:* the spine should say who announces it (the component through the announcer, which the layer table allows, or the hooks) and with which kind. EXPERIENCE should list its `messages.ts` key, which the earlier review also asked for.

4. **[medium] A failed write may actually have landed, and EXPERIENCE doesn't say so.** The spine's Deferred section accepts that a create failing with a network error may have been stored. It reappears on the next successful refetch, and resubmitting creates a second todo. The memlog's flag-10 rationale applies the same uncertainty to every network or 5xx outcome, and the settle refetch reconciles it silently. EXPERIENCE's leads state the outcome as fact ("Couldn't add “{t}”.", "so it's still open", "so it's back in the list"). Flow 4 step 7 has Jun resubmit "Call landlord" after a network failure and get only "Added", which is the duplicate case. EXPERIENCE has no treatment for a later refetch that silently contradicts a failure message: a reverted card flips back, or a restored row vanishes without motion. *Needed (UX side):* acknowledge the accepted risk in Open Items and in Flow 4. Optionally, state that such reconciliations show no message.

5. **[low] AD-14's "No other live region exists" doesn't name the Field status regions.** EXPERIENCE gives each Text field a hidden `role="status"` Field status. AD-14's first exception reads "field validation from the client check, which stays inline (AD-8)". It never says that this inline validation may use a live region. The memlog does say so ("Field statuses stay AD-8 inline validation"), but the spine text does not, so a strict reading of "No other live region exists" fails EXPERIENCE's Field status. *Needed:* one clause in AD-14's first exception, for example "…stays inline (AD-8), including a field-local status region per text field".

### Further low items (not in the top five)

- **Failed-draft storage.** EXPERIENCE keeps a failed edit's draft "per todo until the page reloads". AD-13 provides only the per-call promise. If the card unmounts before the promise settles (for example, a delete confirmed while the edit is pending, which then fails and re-mounts the card), a draft held in that card is lost. The spine leaves the storage place to the component layer, which is fine. EXPERIENCE should name a store that outlives the card.
- **Stale cross-references in EXPERIENCE.** "pending flag 8" (Try again), "proposed in flag 4" (Error row), and the Open Items rows tagged flags 1, 2 and 5 are all still marked **[ASSUMPTION]** although the spine has now decided them. The Architecture flags section has no resolution markers.
- **Capability map R5 wording.** "(confirmed inline in the card, no undo; the confirm sends nothing)" is readable with the "Lives in" column ("`DELETE` on Confirm delete"). Read alone, "the confirm" could be taken as the Confirm delete button. "opening the confirm sends nothing" would be unambiguous. This is cosmetic.

## Inline delete confirm: AD-6, AD-13 and the rest of the spine

**No spine change is needed beyond the R5 row already reworded.**

- **AD-6:** `DELETE /api/todos/{id}` is unchanged. Opening the confirm and cancelling it send nothing, so there is no new endpoint, verb or status.
- **AD-13:** Confirm delete runs the same helper path: optimistic removal, per-todo ordering behind a pending create or `PATCH`, revert and `revertedAt` on failure, `404` as success, and `Deleted` on confirmation. Flag 7 covers a confirm on a card whose create later fails: the queued `DELETE` is dropped silently.
- **AD-11:** the leaving-row exception is already worded "a row the user confirmed for deletion". The confirm's open or closed state is local UI state, not a copy of server state. A confirm-open row removed by a refetch unmounts at once, matching EXPERIENCE's "Confirm open, todo vanishes on refetch".
- **AD-14:** the confirm emits no message. **AD-20:** e2e only gains a click.
- **Ticket side only (Sofia), not spine:** test-strategy K4 ("A todo item's delete control removes it from the list") and E3 ("Delete a todo. It disappears…") need the confirm step. The ticket's Notes assumption "Delete is immediate, with no confirmation dialog and no undo" (initiative-todo-app.md, line 92) still has to be replaced, as EXPERIENCE › Ticket changes already records.
